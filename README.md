# Candidate Triage Tool — GCCX Round 1 Case Study

A small full-stack app that lets a recruiter view, filter, search, and
tag/shortlist candidates from a mock dataset, with one real LLM-powered
feature (a one-line "why this candidate might fit" summary).

Repo layout:

```
backend/    Express API + SQLite data layer
public/     Frontend — plain HTML/CSS/JS, served statically by the API
task2/      Task 2 — ranking function + code review writeup
docs/       AI collaboration log, judgment note, presentation outline
```

## Running it

Requires **Node 22.5+** (uses the built-in `node:sqlite` module — see
"Why no better-sqlite3" below).

```bash
cd backend
npm install
cp .env.example .env        # then fill in ANTHROPIC_API_KEY to use the AI feature
npm start
```

Open `http://localhost:4000`. The SQLite file (`backend/triage.db`) is
created and seeded from `backend/data/candidates.json` on first boot —
delete it if you want a clean reseed.

Without an `ANTHROPIC_API_KEY`, everything works except "Generate fit
summary," which returns a clear 503 instead of failing silently.

## What's built

- **Backend (REST):** `GET /api/candidates` with `q` / `role` / `source` /
  `minExperience` / `tag` query params (all optional, combine with AND),
  `GET /api/candidates/meta` for filter dropdown options,
  `POST /api/candidates/:id/tags` + `DELETE /api/candidates/:id/tags/:tag`,
  `POST /api/candidates/:id/fit-summary` (real Anthropic API call, cached).
- **Frontend:** single page, no build step — search box, role/source/
  experience/tag filters, a card per candidate with skills, notes, tag
  buttons, and an AI summary button.
- **Data layer:** SQLite (`node:sqlite`, built into Node — see below).
  `candidates` table seeded from the provided JSON; a separate `tags` table
  (`candidate_id`, `tag`) so a candidate can carry more than one tag
  (shortlist, follow-up, reject) instead of a single status enum.
  Indexes on `target_role`, `source`, `years_experience` — the columns the
  filter UI actually queries on. Note search is a `LIKE` scan on
  `name`/`notes`; see "Design decisions" for why that's enough here.
- **AI feature:** one-line fit summary generated by a real call to
  Anthropic's Messages API (`backend/services/llm.js`), cached on the row so
  it isn't regenerated (and re-billed) on every page load.

## Design decisions & assumptions

- **REST over GraphQL.** The query shape is "filter/search a flat list" —
  GraphQL's flexibility isn't buying anything here, and REST is less to
  set up in a 5-6 hour budget.
- **Tags as a table, not a status column.** "Tag or shortlist" in the brief
  read to me as wanting more than one bucket per candidate — a recruiter
  might mark someone "follow-up" now and "shortlist" later without losing
  that they were once flagged for follow-up.
- **No `better-sqlite3`.** It needs native compilation (`node-gyp` +
  Visual Studio build tools), which isn't guaranteed to be present on
  whoever's machine runs this. Node 22.5+ ships `node:sqlite` built in —
  zero native deps, same synchronous API shape, nothing lost for a project
  this size.
- **No FTS5 / vector search for notes.** The dataset is <50 rows. A `LIKE`
  scan on an indexed-enough table is correct and instant at this scale;
  reaching for full-text search or embeddings here would be solving a
  problem the current dataset doesn't have. Task 2a is where the "what if
  this needs to scale" thinking actually happens — see below.
- **Fit summary over semantic search** as the one required AI feature.
  Semantic search needs an embeddings pipeline (generate, store, re-embed on
  edit); a per-candidate fit summary is a single API call and gives a
  recruiter faster read value per candidate scanned. Semantic search is a
  natural v2 — noted in `docs/JUDGMENT_NOTE.md`.
- **What I deliberately left out of v1:** auth, pagination, bulk CSV ingest,
  and undo on tag removal. All four matter before this goes near a real
  client — see the judgment note for why they're sequenced the way they are.
